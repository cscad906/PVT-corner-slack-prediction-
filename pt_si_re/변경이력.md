### 클럭 구간은 Dist/Res 가 없는 것이 정상 -- 그렇게 세도록 고쳤다

받는 표에는 **데이터 경로만** 들어 있습니다. 리포트 앞부분의 클럭 구간
(`clock`, `ZCTSNET_*`, `ccd_setup_*` 같은 클럭 트리 넷)은 Dist/Res 가 원래
없습니다. 그런데 2b 와 2c 가 그걸 "빠졌다" 고 세는 바람에, 정상인데도 매번
경고가 떴습니다. 그러면 진짜 문제가 묻힙니다.

이제 **구간을 나눠 셉니다.** 판정은 데이터 구간만 봅니다.

```
  못 채운 줄을 구간으로 나누면
    클럭 구간  : 3108 줄   <- 표에 없는 것이 정상입니다
    데이터 구간: 0 줄  (데이터 구간 전체 8910 줄)
```

`2c` 도 같습니다. 클럭 구간만 비어 있으면 `OK-MERGE` 로 끝납니다.

```
  그중 클럭 구간의 Dist/Res N/A: 3108 (정상 -- 표에 없는 것이 맞습니다)
  [ 정상 ] 3열 5822/8930. 클럭 구간 3108줄은 Dist/Res 가 원래 없습니다.
```

데이터 구간에 빈 줄이 있을 때만 `W-RES` / `W-NA` 가 뜹니다. 그때 보여 주는
넷 이름 예시도 **데이터 구간 것만** 모읍니다 -- 클럭 넷 이름이 섞여 나오면
찾아봐야 소용이 없습니다.

구간을 가르는 규칙은 5a 파서와 같습니다(`clock ` 로 시작하는 줄, `<-` 가 있는
첫 핀 줄, `data arrival time`).

같이 고친 것: `2c` 가 정상으로 끝날 때 `code()` 가 OK- 에서는 그냥 돌아오는
바람에 뒤의 `W-NA` 까지 찍혀 "정상인데 경고" 가 같이 나오던 것을 막았습니다.

### 메모리를 확 줄였다 -- 이제 병렬이 실제로 된다

`--jobs 4` 로 돌렸더니 코너마다 몇 배씩 느려지고 `--watch` 가 "메모리 부족,
스왑 중" 이라고 했습니다. 원인은 **두 단계가 리포트를 통째로 메모리에 들고
있던 것**입니다.

446MB 리포트, net 행 107만 줄로 실측했습니다.

| 단계 | 전 | 후 | |
|---|---|---|---|
| `2c_merge` | 2,430 MB | **288 MB** | 8.4배 |
| `5a_contexts` | 1,818 MB | **47 MB** | 38배 |

**결과는 둘 다 바이트 단위로 같습니다.** 속도도 그대로입니다(2c 14.8→14.6초,
5a 29.1→28.1초). 줄어든 것은 메모리뿐입니다.

무엇을 고쳤나:

- `2c_merge` 는 원본 전체(`lines`)와 결과 전체(`outlines`) **두 벌**을 들고
  있다가 마지막에 한 번에 썼습니다. 줄마다 하는 일이 앞뒤 줄과 무관해서
  한 줄씩 흘려 써도 결과가 같습니다.
- `5a` 의 파서는 net 행마다 dict 하나를 만들어 **전부 쌓아 두고** 마지막에
  썼습니다. 107만 줄이면 그것만 1.8GB 입니다. 경로 하나가 끝날 때 그 경로의
  줄들을 바로 내보내게 했습니다.

### 그래서 --jobs 를 몇까지 줄 수 있나

446MB 리포트 기준으로 코너당 최대치가 **2.4GB 에서 0.3GB** 로 내려갔습니다.

```
전    --jobs 4  ->  약 9.6GB 필요
후    --jobs 4  ->  약 1.2GB 필요
```

메모리가 8GB 만 남아 있어도 4개를 붙일 수 있습니다. 예전에는 2개도 빠듯했습니다.

    돌리는 중에 스왑이 오가는지로 봅니다:

`--watch` 쪽은 원래부터 사용량이 아니라 오간 횟수로 보고 있어서 안 고쳤습니다.

### 0_check 에 장비 점검이 붙었다 (보여주기만 한다)

`--jobs` 를 몇으로 줄지 판단할 근거를 돌리기 전에 보여 줍니다. **동작을 바꾸지는
않습니다** -- `--jobs` 는 여전히 주신 숫자를 그대로 씁니다.

```
1-2. 장비 점검
--------------------------------------------------------------------
  CPU 코어  : 112개
  부하      : 27.91 28.37 27.76 (1분/5분/15분)   <- 코어 수보다 크면 이미 붐빈다
  메모리    : 전체 251GB, 지금 쓸 수 있는 것 138GB
  스왑      : 25GB 사용중  (예전에 밀려난 것. 지금 모자란다는 뜻은 아니다)
  디스크    : nvme0n1  -  SSD/NVMe

  --jobs 를 몇으로 줄까
    2b/2c/5a 는 리포트를 통째로 메모리에 올립니다 (리포트의 약 5~6배).
    ...
    돌리는 중에 느려지면 다른 창에서 확인:
      vmstat 5      si/so 가 0 이 아니면 스왑 중 -- --jobs 를 낮추세요
      iostat -x 5   %util 이 100 에 붙어 있으면 디스크가 병목입니다
```

디스크가 회전식(HDD)인지도 판별합니다. HDD 면 코너를 동시에 돌려도 헤드가
하나뿐이라 총 시간이 그대로라, `--jobs` 를 올릴지 말지가 여기서 갈립니다.

`--dir` 에 코너 폴더를 주면 그 리포트 크기로 **`--jobs` 를 몇까지 줘도 되는지
숫자로** 알려줍니다.

```
    이 폴더 리포트 445MB -> 코너당 약 2.4GB
    쓸 수 있는 메모리 133GB 기준으로  --jobs 38  까지가 안전합니다.
```

### 돌고 있는 작업이 왜 느린지 스스로 판정한다 -- 0_check --watch

현장 화면은 밖으로 내보낼 수 없습니다. 그래서 숫자를 보여 주는 대신 **결론을
말해 주는** 모드를 넣었습니다. `4_all_corners` 가 도는 중에 다른 창에서 돌립니다.

```bash
python3 0_check.py --watch        # 30초 (기본)
python3 0_check.py --watch 60
```

```
     1/6  스왑 233       디스크 대기 0%
     2/6  스왑 22        디스크 대기 0%
--------------------------------------------------------------------
  [ 메모리 부족 ]  스왑을 쓰고 있습니다.

    할 일 : --jobs 를 반으로 낮춰 다시 돌리세요.
```

판정은 네 가지입니다.

| 판정 | 뜻 | 할 일 |
|---|---|---|
| 메모리 부족 | 스왑을 쓰는 중 | `--jobs` 를 반으로 |
| 디스크 병목 | CPU 는 놀고 디스크만 기다림 | `--jobs 1`. 올려도 총 시간 그대로 |
| CPU 경합 | 장비가 이미 붐빔 | 낮추거나 한산할 때 |
| 정상 | 자원 병목 아님 | 리포트가 커서 걸리는 것. 올려 볼 여지 있음 |

`/proc/vmstat` 의 스왑 횟수와 `/proc/stat` 의 iowait 을 두 번 읽어 차이로 봅니다.
마지막 구간만 보면 그때 마침 조용했다는 이유로 잘못 말할 수 있어서, **전 구간
누적**으로 판정합니다.

### 표는 res / dist 두 파일로 고정 — 합본은 없앴다

받는 쪽이 따로 주는 것으로 정해져서, 합본(`resdist_map.txt`) 경로를 걷어냈습니다.
길이 하나뿐이라 "어느 쪽으로 읽혔지" 를 생각할 일이 없습니다.

```
round2/tt0p6v25c_Cnom/
  tt0p6v25c_Cnom.rpt
  cpin_map.txt        받은 Cpin 표    -> 2a
  res_map.txt         받은 Res 표     -> 2b     넷 이름 / res
  dist_map.txt        받은 Dist 표    -> 2b     넷 이름 / dist
```

각각 **2열**이면 됩니다. 헤더는 있어도 없어도 되고, 있으면 열 이름으로 찾으므로
열이 더 있어도 되고 순서가 달라도 됩니다(`resistance`, `length` 같은 이름도
알아봅니다). 없으면 두 번째 열을 값으로 봅니다.

**파일이 갈려 있어 어느 값인지 이름이 말해 줍니다.** 합본일 때는 열 순서가 유일한
단서라 res 와 dist 가 바뀌어도 둘 다 숫자라 에러가 안 났는데, 그 위험이 사라졌습니다.

다른 이름으로 받았으면 `--res-table` / `--dist-table` 로 경로를 직접 줍니다.

한쪽에만 있는 넷은 그쪽 값만 채우고 나머지는 N/A 로 둡니다. 조용히 0 을 넣지
않습니다. 몇 개가 그런지 화면에 찍습니다.

같이 고친 것:

- `0_check.py` 가 점검하는 입력이 `res_map.txt` + `dist_map.txt` 두 개가 됐습니다
- `E-NOTABLE` 문구도 두 파일 기준으로 바꿨습니다

합본이 다시 필요해지면 이 커밋 이전에서 꺼내면 됩니다.

### res 와 dist 를 따로 받아도 된다

한 파일(`net / res / dist`)로 받기로 했는데 실제로는 **따로** 오는 경우가 생겼습니다.
두 파일을 넷 이름으로 합쳐 쓰도록 했습니다.

```
resdist_map.txt              한 파일로 받았을 때.  net / res / dist
res_map.txt + dist_map.txt   따로 받았을 때.       각각 net / 값
```

코너 폴더에 두는 것은 같습니다. **합본이 있으면 합본을 먼저** 씁니다.
경로를 직접 주려면 `--res-table` / `--dist-table` 입니다.

따로 받은 파일은 보통 2열(넷 이름, 값)입니다. 헤더가 있으면 열 이름으로 값 열을
찾고(`resistance`, `length` 같은 이름도 알아봅니다), 없으면 두 번째 열을 값으로
봅니다. 구분자 자동 인식은 합본과 같습니다.

**한쪽에만 있는 넷은 그쪽 값만 채우고 나머지는 N/A 로 둡니다.** 조용히 0 을 넣지
않습니다. 몇 개가 그런지 화면에 찍습니다.

```
  note   : res 에만 있는 넷 115개, dist 에만 있는 넷 0개 -> 그 줄은 한쪽만 채워집니다
  Dist found: 6686   (miss 2244)
  Res  found: 8930   (miss 0)
```

### 확인

합본을 res/dist 둘로 쪼개서 돌린 결과가 합본으로 돌린 것과 **바이트 단위로
같습니다.** 헤더가 붙은 판(`net_name/resistance`, `net_name/length`)도 같습니다.

### --jobs 로 돌릴 때 코너가 시작하는 것도 보인다

병렬로 돌리면 코너 출력을 모아 뒀다가 그 코너가 끝날 때 한 덩어리로 찍습니다
(한 줄씩 내면 4개가 뒤섞여 어느 코너 것인지 알 수 없습니다). 그런데 그러다 보니
**첫 코너가 끝날 때까지 화면이 완전히 멈춰 있어**, 도는 중인지 죽었는지 알 수가
없었습니다.

이제 **시작할 때 한 줄, 단계 하나가 끝날 때마다 한 줄** 찍습니다.

```
  동시에 4개 코너씩 돕니다.
  단계가 끝날 때마다 한 줄, 코너가 끝나면 그 코너 출력이 한 덩어리로 나옵니다.
  시작 [1/4] tt0p6v25c_Cnom              (지금 1개 도는 중)
  시작 [2/4] tt0p65v25c_Cnom             (지금 2개 도는 중)
  시작 [3/4] tt0p7v25c_Cnom              (지금 3개 도는 중)
  시작 [4/4] tt0p8v25c_Cnom              (지금 4개 도는 중)
       tt0p65v25c_Cnom          5a contexts  3초         OK-XCTX
       tt0p7v25c_Cnom           5a contexts  4초         OK-XCTX
       tt0p65v25c_Cnom          5b pairs     12초        OK-XPAIR
       tt0p65v25c_Cnom          5c report    5초         OK-XRPT
끝   [1/4] tt0p65v25c_Cnom   (20초)   남은 시간 약 1분
      ... 그 코너 출력 한 덩어리 ...
```

단계 줄은 **코너 이름이 맨 앞**입니다. 여러 코너가 섞여 나오므로 어느 코너
것인지가 먼저 보여야 합니다. `SKIP` 이나 실패도 그 자리에서 바로 보입니다.

끝날 때 찍는 줄에도 `끝` 을 붙여 시작 줄과 구분했습니다. `지금 N개 도는 중` 은
그 순간 실제로 돌고 있는 코너 수라, `--jobs` 만큼 실제로 붙어 있는지도 보입니다.

하나씩 돌 때(`--jobs 1`, 기본)는 원래대로 출력이 실시간으로 나오므로 안 바뀝니다.

| `E-NORAW` | `context_raw.rpt` 가 없거나 **빔** | 빈 것은 디자인을 안 올린 채 tcl 을 돌린 경우 |
| `E-PARSE` | 그 밖 | 파서 메시지가 배너 위에 찍힙니다. 그걸 먼저 |

`E-MODE` 는 현장에서 제일 흔합니다. setup 으로 만든 출력에 `--mode hold` 를
주는 경우입니다.

```
[ FAILED ] The PT output was made with a different mode.
           5b was told  --mode hold
           but context_raw.rpt holds the other kind of delta delay.
           Either re-run 5b with:   --mode setup
```

시작할 때 두 입력의 줄 수와 mode 를 찍어서, 돌기 전에 어긋남이 보입니다.

```
  PT output : .../context_raw.rpt  (2.9MB)
  5a input  : path_victim_nets.tsv (8930 rows), unique_contexts.tsv (788 rows)
  mode      : setup   (must match the xtalk_all run)
```

`E-NOENGINE` 은 `_engine/` 이 **왜** 빠지는지까지 말합니다. 이름이 밑줄로
시작해서 `cp *.py` 나 `scp *` 가 조용히 두고 가는 것이 매번 원인이었습니다.
